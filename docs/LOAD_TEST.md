# Load test: what was measured, on what, and what it does not prove

Everything below was produced by the scripts in `scripts/load/` and is stored in `docs/load-*.json`. Re-run it: `node scripts/load/build-dataset.mjs` (once, ~16 minutes, ~6 GB on disk), then `node scripts/load/run.mjs`.

**Read this first.** One laptop ran the API, PostgreSQL and the load generator at the same time, while it also ran a browser, an editor and Docker containers. These numbers describe *this machine under this load*. They are a measurement of the code's per-request cost and of its query plans. They are **not** a capacity claim for one million users, and not a prediction for production hardware. See [SCALING.md](SCALING.md) for how they translate into sizing and what stays unproven.

## 1. Setup

| | |
|---|---|
| Machine | AMD Ryzen 5 3400G, 8 logical CPUs, 14 GB RAM, Windows 11, shared with an IDE, a browser and Docker Desktop |
| Software | Node 22.14, PostgreSQL 18.4 (embedded, local disk), API compiled (`dist/main.js`), no Redis (in-process cache) |
| Database | Real schema and migrations, API connecting as the restricted `projectn_app` role **with Row Level Security on** |
| Pool | API database pool of 20 connections |
| Load generator | autocannon, 32 concurrent connections, 15 s per scenario, on the same machine |
| Rate limiting | Scaled up (`RATE_LIMIT_SCALE`) so the limiter does not hide the cost of the work |
| Authentication | Real signed tokens; a different persona per scenario |

### Dataset (synthetic, generated by `scripts/load/dataset.mjs`)

100 institutions × 10,000 users = **1,000,000 users** (1M memberships and role grants), 250,000 projects, 1.25M project members, 1M phases, ~400k submissions, ~800k files, 2M activity-log rows, 500k comments, 500k notifications.

What this is *not*: 1M people using the system. It is 1M registered rows with a plausible shape (a Dean sees ~830 projects, an Institution Admin 2,500, a Student 1). Real data is more skewed (some supervisors lead far more than 12 projects; some tenants are much larger than 10,000 users).

## 2. Results (final run)

Throughput and latency per scenario, 32 connections, zero failed requests in every row:

| Scenario | req/s | p50 ms | p90 ms | p99 ms | max ms | failed |
|---|---:|---:|---:|---:|---:|---:|
| GET /me (student) | 131 | 223 | 305 | 613 | 854 | 0 |
| GET /projects?limit=50 (student: 1 project) | 98 | 315 | 379 | 576 | 712 | 0 |
| GET /projects?limit=50 (supervisor) | 65 | 472 | 599 | 685 | 792 | 0 |
| GET /projects?limit=50 (head: department) | 39 | 775 | 1043 | 1334 | 1415 | 0 |
| GET /projects?limit=50 (dean: faculty, ~830 visible) | 33 | 849 | 1350 | 2021 | 2174 | 0 |
| GET /projects?limit=50 (institution admin: 2,500 rows) | 42 | 746 | 966 | 1397 | 1487 | 0 |
| GET /projects/{id} (supervisor, detail) | 71 | 386 | 583 | 1438 | 1625 | 0 |
| GET /projects/{id}/activity (supervisor) | 111 | 259 | 396 | 653 | 787 | 0 |
| GET /activity?limit=50 (dean, faculty scope) | 112 | 256 | 388 | 471 | 513 | 0 |
| GET /reviews/queue (supervisor) | 65 | 474 | 579 | 834 | 965 | 0 |
| GET /calendar (student, 30 days) | 113 | 263 | 380 | 624 | 707 | 0 |
| GET /notifications/unread-count (supervisor) | 168 | 181 | 245 | 388 | 505 | 0 |
| GET /reports/summary (dean, cached 60 s) | 144 | 201 | 256 | 1069 | 1723 | 0 |
| POST /comments (student) | 54 | 574 | 688 | 918 | 1022 | 0 |
| **mixed profile** (80% reads / 20% writes, 5 personas) | **89** | **343** | **543** | **687** | **732** | **0** |

* **Login** (Argon2id, 19 MiB, 4 connections): 33 req/s, p50 99 ms, p99 378 ms. Deliberately expensive; it is the one endpoint where CPU cost is a security feature.
* **Cold dashboard report** (cache miss on the 250k-project database): 441 to 652 ms.
* **API memory** after the run: 268 MB resident; 20 database connections held.
* **Worker paths** (system role): recomputing health for 400 projects averaged 35 ms each; the durable queue ran **20,166 jobs in 15.9 s (1,269 jobs/s) with two competing runners and 0 jobs executed twice**.

Latency is high in absolute terms because 32 connections are queued against a saturated 8-thread machine (Little's law: 32 in flight ÷ 89 req/s ≈ 360 ms). It says the machine is full, not that a single request needs 343 ms; for one request at a time the cost is much lower (§4).

| pending reviews (supervisor) | 10.3 | 14.6 | none |

The student project page (68 ms, 18 ms of it planning) is the slowest plan. Likely cause: the membership check done by the RLS helper against the largest tables; this was not investigated further. It is the first thing to revisit if students dominate traffic (SCALING.md §6).

## 4. Where the time goes

Per-request cost, measured by sampling the API process's CPU counters and PostgreSQL's per-statement timers (`scripts/load/profile.mjs`), 16 connections, 8 s each:

| Endpoint | req/s | API CPU ms / request | SQL statements / request | SQL ms / request |
|---|---:|---:|---:|---:|
| GET /me | 108 | 13.4 | 7.1 | 2.3 |
| GET /projects (student) | 57 | 25.5 | 11.4 | 43.5 |
| GET /projects (supervisor) | 54 | 34.1 | 11.4 | 31.3 |
| GET /projects (dean) | 33 | 51.7 | 11.8 | 122.7 |
| GET /projects/{id} | 69 | 27.2 | 16.5 | 10.9 |
| GET /activity (dean) | 89 | 14.5 | 6.2 | 8.6 |

Whole-machine CPU split during the mixed read profile (`cpu-split.mjs`, 71 req/s, 15 s, 8 logical CPUs):

| Process | CPU seconds | cores busy |
|---|---:|---:|
| API (Node) | 26.3 | 1.75 |
| PostgreSQL | 16.8 | 1.12 |
| Load generator | 1.1 | 0.07 |
| **Total** | 44.2 | **2.94 of 8** |

That is ≈ 25 ms of API CPU and ≈ 16 ms of PostgreSQL CPU per request (≈ 40 ms in total). The machine was not CPU-saturated by these processes alone (2.94 of 8 cores), so some of the ceiling comes from the other programs running on it and from Node's single-threaded event loop per process. That is why §5 adds instances.

## 5. Adding API instances (same machine)

1, 2 and 4 identical API processes against the same database, one load generator per process, results summed (`scaleout.mjs`):

| API instances | req/s (summed) | worst p50 ms | worst p99 ms | failed |
|---|---:|---:|---:|---:|
| 1 | 48 | 522 | 2941 | 0 |
| 2 | 80 | 741 | 1600 | 0 |
| 4 | 100 | 1238 | 3412 | 0 |

What this shows: the API holds no state between requests, so extra instances help, and PostgreSQL was not the first bottleneck. What it does **not** show: linear scaling. Everything shares eight threads that other programs also use, so growth flattens at ≈ 100 req/s. Treat it as evidence of statelessness, not of a scaling factor.

## 6. Defects this exercise found (all fixed, kept for the record)

| Symptom on the 1M dataset | Cause | Fix |
|---|---|---|
| A membership query took **~20 s** | The RLS helper `pn_ws()` was evaluated once per row | Policies call each helper once per query (`(SELECT pn_…())` InitPlans); sign-in and invite flows moved to a narrow dedicated role |
| `POST /comments` took **~50 s** | A bad query plan under RLS | Rewritten set-returning helpers and added indexes (`projects(workspace_id, created_by_id)`, `project_members(project_id)`, `project_members(user_id)`, `submissions(project_id, submitted_at desc)`, …) |
| The leader-scope helper was slow for callers who are not leaders | Every `UNION` branch always ran | Branches are gated by `EXISTS` on the caller's roles |
| Dataset generation was very slow | Correlated subqueries | Joins and indexes on the temporary tables (now ~16 minutes) |
| An earlier pass reported 35 req/s for the mixed profile | The machine was busy (CPU load 40–80%, 2.5 GB RAM free) | Result kept as `docs/load-contended/`, run repeated; this is why the machine conditions are stated above |

## 7. Limits of this evidence

* **One machine.** API, database and load generator compete for the same CPUs. A separate database host adds network latency to each of the ~7 to 16 statements per request; not measured.
* **Local disk, no network, no TLS, no CDN, no reverse proxy.**
* **No PgBouncer, no real Redis.** The cache and rate limiter ran in process memory.
* **Synthetic data, uniform shape.** Real tenants are skewed; a Dean with 20,000 projects is slower than the 830 measured.
* **15-second bursts.** No soak test, no memory-leak or autovacuum observation over hours or days, no failover test.
* **Closed-loop load (32 connections).** Real traffic is open-loop and bursty.
* **No external services.** Drive, Gemini and e-mail were fakes; real calls are slower and rate-limited.
* **Run-to-run variation is real**: the same code measured 89 req/s on the mixed profile here and 95 req/s in an earlier pass (the contended pass: 35).
